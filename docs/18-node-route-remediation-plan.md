## 0. 基线校正（先看这一节）

### 0.1 站内目前同时存在三套路线系统

| # | 系统 | 数据源 | 规模 | 页面 | 在导航里的位置 |
|---|---|---|---|---|---|
| A | **完整路线图** | `ProjectRoadmap.astro`（硬编码） | **18 节点**，分 6 阶段 | `/roadmap` | 侧栏第二项「完整路线图」 |
| B | 知识路线 | `src/data/journey.ts` | 16 节点（13 主 + 3 分支） | `/roadmap/<id>` | `/roadmap` 页内折叠的 `<details>` |
| C | 学习路线 | `src/data/learning.ts` + `learning-additions.ts` | **6 阶段 31 动作** | `/learn`、`/learn/stage/<phase>`、`/learn/<lesson>` | 侧栏「一步一步做」下的 6 个阶段 |

**A 和 C 是同一件事的两种切法**：A 用 18 个「关键节点」，C 用 6 个「阶段」。而 A 的 18 个节点 id 恰好**全部是 C 的 lesson id 的子集**（18 ⊂ 31）。也就是说：

> **18 个节点 = 31 个动作里的 18 个被挑出来当里程碑；剩下 13 个动作是节点之间的中间步骤。**

路线图页自己也是这么说的（`ProjectRoadmap.astro:1`）：

> 「沿彩色路线，从想法走到交付。**18 个关键节点串起 31 个教学动作**，点击节点开始这一段。」

### 0.2 现在的实际问题

1. **点节点只跳到「其中一个动作」，用户看不到这个节点还有几个步骤。**
   点节点 12「按计划分步开发并测试」→ 进入 `/learn/preview`（1 个动作）。但节点 12 实际包含 4 个动作（preview → interface → save → flow），用户要一路点「已核对，下一步」才慢慢发现。
   → **这就是你说的第 2 条要求缺失**：没有任何一处告诉用户「这个阶段总共有几个步骤」。

2. **每个步骤是一个独立页面，不是可展开的步骤。**
   现在：`/learn/<lesson>` 一个动作一页，靠页脚「已核对，下一步 →」线性推进。
   → **这就是你说的第 3 条要求缺失**：步骤不能点击展开，用户无法在一屏内看到「这个阶段要做几件事、分别是什么」。

3. **步骤内的「预期输出」只有一条，且是整步的，不是每个微操作的。**
   `Lesson.expected` 是单个 `Copy`（一步一条）。`learning-support.ts` 的 `steps: Copy[]` 是纯文本数组，没有「你会看到什么 / 不对怎么办」的结构。
   → **这就是你说的第 4 条要求缺失**：开发阶段每个微操作没有可对照的预期输出和修复思路。

4. **知识库（`/terms` 755 词条、`/library`）没有按 18 节点排序。**
   术语条目不携带节点归属；`lesson.stage` 映射到的是**旧的 16 节点 journey id**（`legacyLessons`），不是 18 节点。
   → **这就是你说的第 5 条要求缺失**：知识库没有按开发节点的时间顺序组织。

5. **`checkpoint` 的分组自相矛盾。** lesson `checkpoint` 的 `phase` 是 `prepare`（所以出现在 `/learn/stage/prepare`），但路线图把它排在**节点 10、阶段 4「制作并验证功能」**里。同一件事在两个地方属于不同阶段。

以 **A（18 节点）为主线骨架**，把 **C（31 动作）** 作为节点下的「步骤」，把 **B（16 节点）** 降级为纯资料。

## 4. 开发节点的「预期输出 + 不对怎么修」（你的第 4 条）

### 4.1 现状

```ts
export interface Lesson {
  actions: Copy[];      // 2–4 条纯文本
  expected: Copy;       // 整步一条
  issues: LessonIssue[] // {check, action, expected, retry}
}
```

`actions` 是字符串数组 → **无法给每个微操作挂预期输出**。`expected` 是整步的，用户在做到第 2 个微操作时没有可对照的仪表。

### 4.2 改法：把 `actions` 升级为结构化

```ts
export interface Action {
  text: Copy;          // 你要做什么（动词开头，主语是读者）
  where?: Copy;        // 在哪里做
  expect?: Copy;       // 你会看到什么  ← 你的第 4 条
  ifWrong?: Copy[];    // 不是这样就怎么办 ← 你的第 4 条
}
```

**强制范围**：节点 10–13（阶段 4「制作并验证功能」）以及节点 16–17（交付）的每条 `Action` **必须**有 `expect` 和 `ifWrong`（≥1 条）。这一条要写进校验脚本。

### 4.3 与现有 `learning-support.ts` 的衔接

`StepSupport.steps: Copy[]` 现在承载「怎么做」的说明文字（比如 `idea` 步的 3 条）。升级后：

- `StepSupport.steps` → 迁移为 `Action[]`（保留原文，补 `where`/`expect`/`ifWrong`）
- `StepSupport.example`（成果样例）→ 移到步骤底部「看示例」
- `StepSupport.recovery` → 并入 `ifWrong`
- `StepSupport.input/output` → 移到步骤头「输入 → 产出」

这样 `learning-support.ts`（1430 行）的内容**不重写，只重新归位**。

### 5.3 讲原理的范例（可直接作样板）

> **为什么刷新一下，我刚填的东西就没了？**（节点 12）
>
> **结论**：因为那些内容只活在浏览器内存里，从来没有被"存"下来过。
> **它干什么**：你在页面上填的每个字，默认只存在于当前这个页面里，一刷新就跟着重建了。
> **为什么**：一个网页分成两半——一半是你看到的界面，一半是记住事情的地方。界面每次刷新都重画一遍，画的时候手里是空的；只有"记住事情的地方"能跨刷新留下来。所谓"接数据"，本质就是给项目装上一个能记住事情的地方。
> **打个比方**：便利贴 vs 笔记本。写在便利贴上的答案风一吹就没了；写到笔记本里，合上再打开还在。
> **这个比方到哪里为止**：笔记本如果放在别人家里（服务器），你必须"联系得上那家人"（有网络）才拿得到。所以——**刷新后没了 = 没存；断网后打不开 = 存了但连不上**，这两件事的修法完全不同。
> **影响你什么选择**：它直接决定你要不要"接数据"。只做展示可以不接；任何"填了要留住""换台设备还想看到"的功能都必须接。
> **和 AI 怎么说**：「我填完点提交，刷新后就不见了。请告诉我现在存在哪里；如果只存在浏览器里，说明要加什么才能真的存下来。」
> **你怎么验证**：① 填一条 → 刷新，还在吗？② 关浏览器再打开，还在吗？③ 换设备，还在吗？④ 断网打开，提示是什么？

这条就是你要的「知其所以然」：**它不给「后端是处理数据的服务端」这种定义，而是让用户理解「为什么会有后端这个东西」。**
