# 内容体系、首期选题与编辑标准

状态：内容规划与样稿，尚未发布。根据本轮四类项目和 12 项主题补充；完整路线、面向读者的白话内容和提示词见 [站点总规划](site-blueprint.md)。本文件负责编辑标准、基础选题和词条模型，不再定义一套独立的站点结构；12 个独立板块的布局和分层以 [页面与内容架构](page-content-architecture.md) 为准。

专业术语保留标准英文便于与工具界面对照，主解释用普通中文。

## 1. 通用写作标准

每条内容只解决一个主要问题。用“你准备……时会遇到……”开头，再讲做法；不以百科定义开场。解释一个词后必须回答：什么时候用得上、它影响什么选择、应该怎样和 Agent 说、如何验证。

不要用类比替代事实：类比之后补一条边界。不给“一个提示词就能做好项目”“不懂代码就完全没有风险”的承诺。不展示实现代码、堆砌命令、以源码截图作普通人的验收凭据。隐私、费用、公开发布等提醒只在用户要做相关操作时出现。

一个样稿至少包含：问题、适用范围、前提、3–5 个动作、完整话术、可见成功标志、失败下一步、相关内容。价格、功能限制、界面步骤必须附官方来源和核验日期；未知就标未知。

## 2. 共同检查阶段：按四类项目展开

下表是编辑组织的共同基础，不要求四类项目都机械照搬八步。网站、小程序、手机和电脑的具体顺序、设备要求及交付方式以总规划第 2–5 节为准。

| 阶段 | 用户要回答的问题 | 交付物 | 如何判断可继续 |
| --- | --- | --- | --- |
| 1 明确用途 | 谁在什么情况下用它？ | 一句话目标和一个真实场景 | 另一个人能复述用途 |
| 2 缩小第一版 | 第一次必须完成哪件事？ | 必须做 / 以后做清单 | 有一条从进入到完成的核心流程 |
| 3 选择工具和方案 | 安装、费用、数据、多人协作有什么限制？ | 选择理由与限制说明 | 知道依赖什么账号与服务 |
| 4 讲清界面和行为 | 页面有哪些？点击后发生什么？ | 页面清单、示例、交互描述 | 包含正常、空、失败状态 |
| 5 小步制作 | 先交付哪一条可用流程？ | 可打开的小版本 | 先走通一个流程，再扩展 |
| 6 亲自验收 | 它真的完成任务了吗？ | 操作清单与问题记录 | 用新数据重试可得到预期结果 |
| 7 排查和修改 | 现象、预期和实际哪里不同？ | 证据、单项修复与复测记录 | 原问题解决且相关功能仍可用 |
| 8 交付和维护 | 谁能访问？如何更新与恢复？ | 地址、限制、备份和交接说明 | 换设备核对访问；明确恢复办法 |

## 3. 工具选择：6 篇首期指南

1. 网页里直接做、安装在电脑里做：我更适合哪一种？
2. 做一个介绍页，与做一个会保存资料的应用，工具要求有何不同？
3. 已经有项目时，怎样判断工具能不能继续接手？
4. 工具订阅费、AI 使用费和网站运行费有什么区别？
5. 选择前检查：地区可用性、能否导出、能否本地保存、能否迁移。
6. 怎样先用一个小任务试用，再决定是否长期使用？

选择器询问项目类型、现有项目、操作系统、安装意愿、预算范围、是否需要共享数据、是否需要拿走项目文件。优先排除不满足硬条件的类型，再展示权衡；同条件可输出两个选择，不假装存在唯一答案。

品牌工具卡字段：适合谁、不适合谁、首次使用步骤、费用类型、导出能力、环境要求、官方来源、核验日期。尚未核验品牌不进入推荐结果；工具卡过期要提示重核，旧价格不得继续作为购买依据。

## 4. 沟通模板：12 个首期场景

| 模板 | 必填信息 | 输出内容 |
| --- | --- | --- |
| 把想法变成第一版 | 使用者、问题、成功动作 | 目标、范围、待澄清项 |
| 开工前先出方案 | 已知需求、约束 | 流程、选择理由、验收步骤 |
| 描述一个页面 | 页面目的、必须展示的信息 | 区域、顺序、关键操作 |

| 使用参考图 | 学什么、保持什么、不要什么 | 可执行差异说明 |
| 只修改一个地方 | 当前表现、目标表现、影响边界 | 小范围修改任务 |
| 反馈效果不对 | 操作步骤、预期、实际 | 可复现的问题说明 |
| 让 Agent 先排查 | 现象、环境、最近变化 | 证据和检查顺序 |
| 防止越改越乱 | 最后可用版本、当前问题 | 暂停扩展、回到检查点的计划 |
| 检查是否完成 | 使用场景、成功标准 | 操作验收清单 |
| 新会话接手 | 已完成、未完成、限制、相关文件 | 简短交接说明 |
| 上线前确认 | 访问人群、数据、成本、维护方式 | 发布前核对与后续维护任务 |

统一输出骨架：我想完成【目标】；使用者是【人群】；当前情况【事实】；本次只做【范围】；保留【限制】；操作【步骤】后应看到【结果】；不确定时先列出需确认的事项；完成后说明验证结果和剩余限制。

## 6. 三个术语样稿

### 前端：用户看见并操作的那一部分

你做活动报名页时，标题、日期、输入框和“提交报名”按钮都属于前端。你需要说明放什么、怎么排列、点完出现什么。

可以这样说：“报名页显示活动名称和日期，填写姓名后才能提交。提交时显示处理中；成功后显示确认信息；失败时保留我填的内容并提示重试。”

检查：空着姓名是否阻止提交？失败后内容是否仍在？不要只看按钮是否漂亮。边界：页面出现‘报名成功’不证明记录已真实保存，需要再检查管理端或保存结果。下一步：看“后端”和“数据库”。

### 后端：在背后处理请求、数据和权限的部分

如果报名结果要让组织者统一查看，就需要可靠的共享保存和访问控制。它可以由托管服务承担，不一定自己维护一台服务器。

可以这样说：“报名信息需要跨设备保存，只有组织者能看名单。请说明准备存在哪里、如何验证真实保存、普通访客为何不能看到名单，以及需要哪些服务费用。”

检查：换设备能否查看授权的数据？未登录访客是否看不到名单？用虚构测试信息操作。边界：只做公开介绍页时，不必为了‘完整’单独搭建后端。下一步：看“数据库”和“权限”。

### 技术栈：完成项目所使用的一组技术和服务

它会影响项目如何开发、在哪里运行、需要支付什么费用，以及以后由谁维护。普通人先讲需求和限制，让 Agent 说明选择理由，不需要先背框架名。

可以这样说：“我先做个人作品展示站，自己更新内容，不需要登录或收集用户资料。请选维护步骤少、可以导出文件的方案，解释部署、更新、费用和以后增加报名功能需要改哪些部分。”

检查：Agent 是否把每种技术对应到真实需求？有没有解释不确定的费用和维护步骤？边界：没有适用于所有项目的‘最好技术栈’；当前需求变化时应重新评估。

## 7. 12 张首期排查卡

| 现象 | 先确认 | 交给 Agent 的证据 | 成功判断 |
| --- | --- | --- | --- |
| 页面打不开 | 地址、是否启动、出错时间 | 完整提示、发生步骤 | 相同地址重新打开成功 |
| 点击按钮没反应 | 是否禁用、是否缺必填项 | 点击前后画面和预期 | 操作得到可见结果 |
| 保存后刷新没了 | 是临时展示还是持久保存 | 新增、刷新、重开的步骤 | 重开仍保留；共享需求需跨设备验证 |
| 改完页面没变化 | 是否打开正确版本 | 当前地址和本次修改 | 指定变化在目标版本出现 |
| 手机显示挤在一起 | 手机宽度和具体区域 | 截图与设备信息 | 无横向溢出且可操作 |
| 修改 A 却弄坏 B | 最后正常状态和修改范围 | A/B 的复现步骤 | 两个流程都能通过 |
| 登录不了 | 账号、登录方式、具体提示 | 脱敏提示与时间 | 正确身份进入正确页面 |
| 没有访问权限 | 当前身份和访问对象 | 预期权限、错误提示 | 授权用户可访问，未授权用户仍被拒绝 |
| AI 忘记要求 | 当前目标是否还在上下文 | 需求摘要与偏离点 | Agent 先复述，再按限制完成 |
| Agent 一直修不好 | 是否反复无证据猜测 | 尝试过什么和各次结果 | 找到证据支持的原因，再单项复测 |
| 本地正常，上线不行 | 环境与配置差异 | 预览/线上地址、脱敏错误 | 在线核心流程通过 |
| 发布后需要撤回 | 上一可用版本和当前影响 | 版本、数据变化、恢复目标 | 页面恢复且明确数据是否另外处理 |

排查卡必须用“检查结果 A → 下一步 A；结果 B → 下一步 B”的分支，禁止一上来让用户删文件、清空数据库、关权限或反复重装。把症状与原因分开，不根据一句报错就认定根因。

## 8. 组件词典迁移与内容维护

保留 212 个稳定 ID 和 25 个分类，逐项记录中文名、英文名、别名、日常搜索词、适用场景、不适用场景、提示词、演示标识和验证状态。加入容易混淆的对照：Tabs/Slider、Select/Combobox、Dialog/Drawer、Tooltip/Popover。

第一批重点校准 12 个词条：下划线 Tabs、滑动指示 Tabs、主按钮、文本输入、Select、Combobox、Switch、Slider、Dialog、Drawer、Toast、基础表格。迁移时再核对具体 ID，不按显示顺序绑定。

内容状态为 draft / reviewed / published / needs-review；演示另设 illustration / partial / verified，不能混为一个状态。稳定解释至少半年复核；工具与界面操作指南至少每月复核，收到变更信息提前复核；过期条目暂停进入工具推荐结果。

主内容对象包括 guides、terms、templates、troubleshooting、tools、components；案例作为 guides 的 subtype。共同字段为稳定 ID、标题、问题描述、别名、受众、阶段、状态、来源、更新时间、核验时间、相关 ID。发布检查引用必须存在，不能复制术语解释到各处制造多套真相源。

## 10. 扩展内容模型

教程增加 projectTypes（web / mini-program / mobile / desktop）、topic（沟通、方案、界面、资料、检查、上线、照看等）、stage、prerequisites、deliverable、successChecks、failureNext、promptRefs。路线用有序稳定 ID 引用教程，不复制共用正文。

平台字段与项目类型分开：小程序为 WeChat / Alipay / Douyin，手机为 Android / iOS，桌面为 Windows / macOS。无法确认的平台能力以 needs-review 标记，不能默认与同类平台相同。

方案内容另设 stacks 集合，与 tools（AI 助手）区分。术语继续使用 terms；后端、测试、上线和维护是 guides 的主题，不重复建立四套内容存储规则。

## 11. 分层写作与板块归属

每个板块必须同时展示中文标题、专业名称和一句白话解释。专业名称保留以便用户看懂 AI 工具的说法；白话解释直接可见，不隐藏到悬停帮助里。

- L1 概览只负责是什么、有什么用、从哪里开始。
- L2 主题/阶段列具体问题、前提和产物，帮助选择。
- L3 行动页包含例子、动作、完整提示词、成功判断和失败下一步。
- L4 深入解释提供术语边界、相关概念和来源，不阻断主要行动。

内容字段补充 primaryModuleId（唯一主归属）、relatedModuleIds、level、termRefs、plainSummary；模块 M01–M12 的顺序和路由见页面架构。术语解释用稳定 ID 维护，概览标题下取短解释，正文首次出现时取相关解释。不得为了各板块分层再复制多套不同定义。

发布前逐模块填清第一屏、下面的区域、子主题、例子类型、提示词位置及检查方式。栏目概览不是空链接集；案例与演示的实际验证状态要独立于文章审核状态。
