# 全流程教学缺口审查与待确认整改方案

状态：待用户确认；本次只审查和整理，不修改站点实现，不宣称完成修复。
审查基线：ba1070c，2026-09-27；当前 31 步经 learning.ts、learning-additions.ts、learning-prompt-review.ts 合并后的实际数据。

## 结论与证据边界

当前站点适合作为 AI 协作流程提纲，还不足以证明零基础用户可以依靠它完成自己的项目。最严重的问题不是文案不够长，而是把多个需要决策、操作和验证的过程压缩成“让 AI 完成”，没有提供可跟随的分支和中间产物。提示词把任务交给 AI，不等于网站把方法教给了用户。

本次逐条读取了全部 31 步的操作、提示词、完成条件、问题处理和去向，并交叉检查学习页组件、模板校验、进度逻辑、部署资料及四类项目适用说明。平台分发边界核对了官方资料。未在外部 AI 工具中重跑 31 步，也未进行真实新手测试；以下区分源码确定的问题与需要试跑确认的教学风险。

现有内容并非全部无用：想法模板、范围控制、需求与用户故事、人工反馈—修复—复测、保护已有文件、真实结果与 AI 自述分开，这些保留。资料页已提到环境变量、费用、签名/平台要求、测试安装与备份，不能说全站从未提到；问题是这些提醒没有落成主线内可执行、可验证的教学分支。

## 一、已经确认的结构性问题

1. **缺少完成全部开发任务的循环。** 第 16 步明确只做第一项，随后固定进入界面调整、保存、流程测试。没有“本任务验收→下一未完成任务→全部本版任务完成”的主线路径。第一项完成不能推出项目已完成。
2. **路线名义通用，操作仍以 Mac 与学习记录网站为中心。** 访达、learning-journal、浏览器页面、输入框与历史列表多次出现；提示词虽部分做了不适用判断，标题、位置、求助仍可能误导其他项目。
3. **项目类型和交付可行性进入主线过晚。** 做完才选择渠道，可能这时才发现没有目标设备、构建环境、开发者账号、分发资格或预算。早期先确认可行方向，后期再确认正式交付细节；不要求初学者一开始决定所有技术。
4. **上线准备没有分层。** 第 28 步混合构建、配置、部署、安装、试运行，缺少每一项的输入、操作入口、产物和失败处理。
5. **进度不能表达依赖和失效。** 当前主要保存 completed 字符串列表，点击某些分支即可记完成；没有“不适用/待人工验证/阻塞/版本变更后待复查”。模板改动会使复制失效，但学习步骤通过状态不会随需求或版本变化失效。
6. **可选路线位置不合理。** GitHub Pages 准备出现在第 30 步，即正式交付第 29 步之后；主线又从第 29 步直接到维护。应是静态 Web 交付下的前置分支，不能编号造成先发布再选方案的错觉。
7. **个别提示词与求助互相冲突。** 第 20 步提示词要求只测试、不修复，其求助却让 AI 复现后修正；第 23 步只记录反馈，其求助让 AI 增加诊断，可能修改代码。修复应转入明确步骤，或显式界定只读诊断。
8. **“确认生成”不保证材料就绪。** 当前主要查空文本和未替换占位符，所有占位替换为“尚未确定”也能通过；第 28 步原模板没有实际待填字段，确认可能只复制原文。关键输入缺失不能当作可执行的专属方案。
9. **验证口径仍偏结构。** 既有校验覆盖字段、路由、模板操作和文本约束；旧审查明确没有外部 AI 实跑。不能据此说提示词能带新人完成项目。
10. **多处内容独立维护易漂移。** 主线、追加数据、覆写、求助、路线图和资料重复描述行为。必须一起审查；当前桌面项目简介仍强调已有网站经验，而适用说明已不要求该前提。

## 三、交付必须先讲懂的关系

开发仓库是“配方、制作过程与版本记录”；构建是按照当前项目的规则生成可运行或可分发的产物；部署是把所需产物和配置放到目标环境并启动；发布是正式向目标用户开放；上线验收是从目标用户入口核对结果。

不能把“生产包”讲成所有项目都有的一个压缩包：

- 静态 Web：常见产物是 HTML/CSS/JS/图片等目录；无构建工具的简单站点可能直接交付源文件。
- 含后端 Web：可能是客户端静态资源加服务端程序，也可能是框架适配器生成的服务函数或容器；数据库、配置、持久存储和外部服务不会自动全部变进一个包。
- Android：开发调试产物、面向直接安装的签名 APK、商店用 AAB 等用途不同；不能让用户拿 AAB 当普通安装文件。
- iOS：归档、上传商店、TestFlight、正式审核发布是不同状态，不是把任意 IPA 放网站就能供所有人安装。
- 桌面：按操作系统与处理器架构生成适合的应用/安装器，签名、公证或商店要求按渠道处理。
- 小程序：使用所选平台的开发工具、预览/体验、上传、审核和发布，不能照搬 Web 托管。

还需区分：本地开发仓库、远程源码仓库、构建产物、生产运行环境、用户数据库。代码回滚不等于用户数据恢复，推送仓库不等于完成发布；若平台绑定了自动部署，推送可能触发发布，应在前面明确说明。

## 四、交付分支应补全哪些动作

### Web：静态前端、前端加外部服务、包含服务端运行

1. 从项目文件与实际需求判断是否需要服务端运行、数据库、文件存储或第三方 API。纯静态托管可承载前端，但不能因此省略外部服务的生产准备。
2. 确认已测试版本、目标平台支持的运行方式、账户、资源限制、预算；平台默认域名可先试用，自有域名是按需项，不强迫买服务器或域名。
3. 明确源代码目录、构建命令、运行版本、依赖锁定方式、输出目录。构建在本机还是托管平台执行，应二选一讲清并说明同一版本如何对应。
4. 生产配置逐项说明名称、用途、在哪里填、由谁提供、是否可公开，以及构建时/运行时读取的区别。不要收集真实密钥到本站或可复制文档。
5. 按需准备生产数据库、结构迁移、访问规则、文件存储、API 地址、登录回调、CORS 和外部服务正式配置；测试数据与生产数据分开。
6. 实际运行构建，展示成功输出、真实产物位置、失败日志获取方法。不能写死所有框架都是 npm run build 和 dist。
7. 使用对应目标的预览或测试环境试部署。含服务端项目检查启动命令、端口、健康检查、持久存储与日志；仅在需要时讲容器。
8. 检查首页、子页直接访问/刷新、资源路径、HTTPS、登录/登出、读写、权限和适用的上传/外部调用；不能只开首页。
9. 如选自有域名，解释域名与托管的关系，按平台给 DNS、绑定、证书与结果核对步骤。
10. 保存前一可用版本、回滚方法及数据兼容方案；完成最终发布确认、正式入口检查及维护交接。

### Android

选择直接下载或具体商店→核对当前渠道/地区的开发者验证及资格→准备应用标识、版本、权限说明、签名资产→构建渠道所需的 release 产物→保存安全的签名备份→在目标真机新安装、覆盖升级、重启及权限拒绝测试→准备下载页或商店材料→按渠道发布→从真实下载/商店入口安装验证。App 依赖后端时还必须完成 Web 服务端相应步骤。

### iOS/iPadOS

先确认目标地区、账号资格、可用 Mac/Xcode 或支持的云构建与真机测试条件→应用标识、签名/描述文件和能力配置→归档与上传→TestFlight 测试→按需商店资料、隐私信息、审核账号和正式提交→处理审核问题→正式发布→真实设备验收。网站分发等替代渠道单列资格分支，不能成为默认通用路径。

### 桌面应用

先选 Windows/macOS（如承诺 Linux 再单列）与架构→选择直接下载或商店→按目标配置构建与打包→按渠道处理签名及 macOS 公证等要求→在没有开发环境的目标机器测试新安装、启动、文件权限、卸载与更新→确认用户数据保留→制作下载页/商店资料→真实下载入口测试→安排更新与恢复。不要教用户关闭系统保护来“通过”。

### 小程序

先选微信/支付宝/抖音等具体平台→官方账号、主体与目标类目资格核对→开发者工具和项目标识→后端与请求域名/平台能力按需配置→预览与体验成员→真机测试→版本上传和审核资料→审核/驳回处理→发布→目标用户真实入口测试。各平台的按钮与材料不能共用一套假定说明；实现时必须针对选定平台核对当期官方要求。

### 本机自用或脚本

可以不公开，但仍要给启动入口、运行依赖、文件路径、输入输出示例、停止方式及适用的数据备份；定时运行还需要机器在线、权限、任务日志和失败处理。不得把不公开误写为不需要交付准备。

## 五、页面与提示词的整改标准

主线保留六阶段，但不再强行要求所有用户走同一份 31 页。编号采用阶段/任务/子步骤，明确必做、按条件出现和可选项；允许浏览其他路径，未知关键条件给说明和返回入口，不靠一个“尚未确定”绕过准备。

每个复杂父步骤先显示：这是哪一步、为什么做、做完获得什么、需要先准备什么、选择哪个分支。进入分支后每个子步骤只完成一个可判断动作：

1. 在哪里做：本站、AI工具、终端、官方控制台、手机还是目标电脑。
2. 谁来做：用户操作、AI可执行、账号持有人确认；AI无权访问时提供人工替代路径。
3. 用什么：自动带入已确认的项目条件；本步真正缺失的输入单独填写并给示例。
4. 怎么做：具体动作、命令的适用前提或已核验的界面入口；说明为何需要。
5. 得到什么：真实文件/目录/版本/地址/平台状态，用图和合格例子辅助。
6. 怎么确认：操作、预期、实际、证据位置；本人检查与 AI 检查分开。
7. 出错怎么办：按可见症状进入恢复分支，返回原步骤复查。

提示词分为准备检查、执行当前动作、只读诊断、结果记录；不把互相冲突的职责塞在同一段。每条绑定前置材料、本次范围、产物、验证与停止条件。不是每步都需要 AI 提示词：买账号、选设备、商店声明和真实人工试用应明确由用户处理。

模板的“专属”必须体现在已选平台、路径、版本、目标和本步输入；只点击确认复制同一段通用话不算。必须输入的关键项与可暂缓项分开；无需填写的纯执行指令应直说，而不是假装有表单。

## 六、拟采用的执行顺序与验收（待确认）

1. **先重排依赖与分支。** 完成平台/工具选择、开发任务循环、两次交付评估、发布与修复返回。输出整张流程和 31 步迁移对照；保留旧链接/草稿，不沿用失去依据的完成状态。
2. **先做一条完整 Web 样板。** 静态 Web 全流程跑通；另做带后端、账号和数据的样板，证明不是只对静态页面成立。截图中的交付步骤优先展开为可操作子流程。
3. **逐个平台补齐并试跑。** Android、iOS、桌面、小程序按实际可用工具和设备分别建立完整路径。没有设备、账号或发布资格的环节标明未实测，不用模拟结果冒充；不能声称一版已证明所有工具和平台都可完成。
4. **同步所有模板、求助和资料入口。** 全部 31 步逐条对照，不仅修第 28 步；纠正旧范例、矛盾提示与默认路径。
5. **验证真实教学链。** 用全新项目从第一步开始，只依赖页面和模板；记录第一次卡点、AI实际输出、人工补充解释及结果。需要站外口头补课才能走完的地方仍列为缺口。正式公开/账号费用/协议由持有人决定，不为了测试而越权发布。
6. **再做真实新手体验。** 观察能否独自解释并完成关键动作，而不仅是复制成功。代码、界面、AI实跑、目标环境、真实用户理解各自记录证据。

建议本次确认的是：同意以上全流程整改范围与方法；先交付可实测的完整样板和分支骨架，再扩展平台，不能再以模板齐全或校验通过作为最终验收。
