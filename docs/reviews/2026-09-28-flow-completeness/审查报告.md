## 2. 🔴 阻断：节点 06 拿不到 `idea.md`

### 2.1 证据

代码里 31 步的**真实执行顺序**（`learning.ts` 在模块加载时把 `checkpoint` splice 到 `open-project` 之后）：

```
1.idea  2.description  3.tool  4.folder  5.open-project  6.checkpoint  7.first-file
8.clarify  9.scope  10.requirements  11.stories  12.prototype ...
```

文件依赖：

| 文件 | 创建者 | 读取者 |
| --- | --- | --- |
| `idea.md` | **`checkpoint`（第 6 位）**、`clarify` | `first-file`(7)、`clarify`(8)、`scope`(9)、`requirements`(10) |

而 `clarify` / `scope` / `requirements` 的提示词**第一句都是**：

> 「先检查能否读取 `idea.md`。缺失或无访问能力时，明确缺项与需本人操作的入口，**停止本步执行**，不编造文件或前序结论。」

`checkpoint` 的提示词正是那个把项目描述保存成 `idea.md` 的步骤：

> 「本步只准备项目起点。核对当前文件夹，将以上描述保存为 **idea.md**；已有文件时先核对差异，不覆盖。检查 Git…建立仅包含本步文件的起点提交。」

### 2.2 我建的节点顺序把它排到了节点 10

| 节点 | 我给的步骤 | 依赖 `idea.md` |
| --- | --- | --- |
| 05 在工具中打开项目 | `open-project`, **`first-file`** | `first-file` **需要**，但此时不存在 |
| 06 澄清需求与第一版范围 | **`clarify`** | **需要 → 停止** |
| 07 形成需求与用户故事 | `requirements`, `stories` | 需要 → 停止 |
| 08 确认界面与技术方案 | `prototype`, `choose-stack` | 需要 `requirements.md` → 拿不到 |
| 09 制定开发计划 | `plan` | 需要 `requirements.md`、`design.md` → 拿不到 |
| **10 准备 Git 与项目规则** | **`checkpoint`** | ← **文件在这里才被创建** |

**用户在节点 05 就会第一次遇到"文件不存在"，节点 06 明确被"停止本步执行"拦住，一路堵到节点 10。**

### 2.3 根因：路线图的节点顺序 ≠ 学习数据的执行顺序（不是我这轮才有的矛盾）

路线图（18 节点）把「准备 Git 与项目规则」放在**第 10 位**，属于「阶段 4 制作并验证功能」。而学习数据把它放在**第 6 位**，紧跟「在工具中打开项目」。

数据里有一行注释说明了后者的意图：

> `// Resolve the cooperation baseline before the first write test; preserve old routes.`
> （在第一次写文件测试之前先建立协作基线）

而且在旧的实现里，路线图只是一个**「里程碑概览」**——点节点跳到 `/learn/<对应课程>`，18 个节点和 31 步是两套并行编号，从来没有被当成同一条线性路径。**上一轮把 18 节点改造成主线脊柱之后，这个矛盾才变成阻断。**

### 2.4 两个修法（需要你选）

**修法 A（推荐）：把「准备 Git 与项目规则」移动到节点 06，节点重新编号。**

```
01 idea              02 description        03 tool
04 folder            05 open-project       06 准备 Git 与项目规则（checkpoint + first-file）
07 clarify           08 requirements(+stories)  09 prototype(+choose-stack)
10 plan              11 environment        12 preview(+interface/save/flow)
13 accept(+test/restart) 14 delivery       15 release-review
16 package           17 live-check         18 maintain
```

- 优点：符合数据设计意图（先建基线再改文件）、文件依赖全部满足、每个节点步数更均衡（1/1/1/1/1/**2**/1/2/2/1/1/4/3/1/1/2/1/1）
- 代价：**与你现在这张路线图的节点编号不一致**（图上 10 是 Git，改后是 06）

**修法 B：保留路线图编号，改提示词。**
让 `clarify` 在 `idea.md` 缺失时**自己创建**（用节点 02 的项目描述），不再"停止本步执行"。

- 优点：不动你确认过的路线图
- 代价：违背"先建基线再改文件"的设计意图；节点 02→10 之间的所有改动都不在版本控制与 AI 规则约束之下；且要改 4 份提示词的入口逻辑

## 3. 🟠 顺序缺陷

### 3.1 修复回路的入口节点少了两个

数据里 `package` 与 `live-check` 也有指向 `feedback` 的分支：

```
accept → feedback      repair → feedback        release-review → repair-plan
package → feedback     live-check → feedback
```

但我的 `repairEntryNodeIds` 只有 `['accept','release-review']`。**结果：用户在节点 16（准备交付物）或节点 17（交付上线）点「记录反馈」，会跨页跳到节点 13**，而他正在做的事突然换了位置。

修法：改为 `['accept','release-review','package','live-check']`，让修复回路在这 4 个节点都就地展开。

### 3.2 `publish` 被当成了线性步骤

`publish`（GitHub Pages）的提示词写着：

> 「只判断是否适合 GitHub Pages…**适合时列出实际构建命令、输出目录和 Pages 设置操作，供本人核对。本步只准备方案，不创建远程仓库、不推送、不发布。正式执行统一进入交付步骤并确认目标与授权。**」

产出写「→ **返回第28步**」。也就是说它是一个**从"准备交付物"出发、办完就回到原处的可选前置分支**，不是线性第 2 步。

修法：把 `publish` 从节点 16 的线性步骤改为节点 16 内的条件分支（只在"静态网站"交付方式下展开），或保留为可选步骤但明确标注「可选 · 只做方案，完成后回到本节点」。

## 6. 提示词质量总评（正面）

31 份提示词里 **30 份存在**（仅 `idea` 无，设计如此）。整体质量明显高于同类内容，共同特征：

1. **统一的前置检查句**：「先检查能否读取 X。缺失或无访问能力时，明确缺项与需本人操作的入口，停止本步执行，不编造文件或前序结论。」——这一句直接防住了 AI 编造前序成果。
2. **明确禁止越界**：「本次不写用户故事、技术方案或代码」（`requirements`）、「不开发、不制定开发计划」（`clarify`）、「不推送、不发布」（多处）。
3. **要求等待本人确认**：「先展示清单供本人确认；确认后保存…」（`scope`）、「任务先标待本人核对；收到本人明确结果后才标通过」（`preview`）。
4. **区分实现与验证**：「不以 AI 声称完成代替」（`accept` worksheet 字段说明）。
5. **不伪造未执行的事**：「不能把准备完成当上线成功」（`live-check`）、「未安装项不冒充完成」（`environment`）。

这 5 条是本站在"让 AI 真的按步骤办事"上最扎实的资产，整改时**不要动**。
